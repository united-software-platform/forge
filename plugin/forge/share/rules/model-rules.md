# Нормы модели forge

Обязательные нормы формата модели, эволюции её контракта и выпуска миграций. Документ — данные
поставки плагина: в проекте-потребителе он выдаётся вызовом `forge norms`, одно правило — вызовом
`forge norms --rule КОД`. Понятия раскрыты в [глоссарии](../docs/glossary.md).

## Формат модели

### Раскладка каталогов

**[MDL-001]** Модель лежит в каталоге `model/<пакет>.v<MAJOR>/`, где `MAJOR` — старший разряд
версии. В каталоге — манифест `_manifest.yaml`, каталог `types/` с одним файлом на тип узла
(Node Type) и файл сигнатур связей `relations.yaml`.

```text
model/
  <пакет>.v1/
    _manifest.yaml         имя модели, версия, перечисления
    types/
      ord.yaml             один файл на тип узла
    relations.yaml         сигнатуры связей
  releases/
    1.2.0.json             дескрипторы выпущенных версий
```

**[MDL-002]** Каталоги разных старших разрядов существуют одновременно и сравнению между собой
не подлежат. Средний и младший разряды живут внутри манифеста.

**[MDL-003]** Дескриптор (Descriptor) выпущенной версии лежит в `model/releases/<версия>.json`
и пишется только инструментом при выпуске.

### Манифест

**[MDL-004]** Манифест содержит имя модели `model`, версию `version` вида `X.Y.Z` и перечисления
(Enum) `enums`.

```yaml
model: forge.reqs
version: 1.2.0

enums:
  req_status:
    id: 1
    values:
      - { id: 1, name: DRAFT }
      - { id: 2, name: APPROVED }
```

**[MDL-005]** Значение перечисления записывается заглавными латинскими буквами с подчёркиваниями
и имеет собственный номер: имя значения может измениться, номер — нет.

### Тип узла

**[MDL-006]** Код типа узла `type` — 2–10 заглавных латинских букв. Из него выводятся код
экземпляра (`ORD-001`) и имя таблицы ревизий (`ord_revision`).

**[MDL-007]** Номер типа узла `id` неизменен.

**[MDL-008]** Имя типа узла `name` задаётся русским `ru` и английским `en`; оба обязательны.

```yaml
type: ORD
id: 3
name:
  ru: Заказ
  en: Order

fields:
  - { id: 1, name: number, type: text, required: true }
```

### Поле

**[MDL-009]** Номер поля (Field) `id` уникален в пределах типа и неизменен; именно он является
идентичностью поля. Это позволяет отличить переименование от удаления с добавлением и не потерять
данные.

**[MDL-010]** Имя поля `name` записывается строчными латинскими буквами с подчёркиваниями. Имя
может меняться: смена имени при том же номере — переименование, а не новое поле.

**[MDL-011]** Тип поля `type` — один из скалярных `text`, `int`, `bool`, `timestamp`, `uuid`,
либо `enum.<имя>` — ссылка на перечисление, либо `ref.<ТИП>` — ссылка на тип узла.

**[MDL-012]** `required_since` — средний разряд версии, начиная с которой поле обязательно.
Экземпляры прежних версий остаются валидными без значения поля.

```yaml
- { id: 5, name: rationale, type: text, required: true, required_since: 2 }
```

### Сигнатура связи

**[MDL-013]** Сигнатура связи (Relation Signature) задаёт домен `from` и кодомен `to`; оба
обязательны и непусты.

**[MDL-014]** Кардинальность (Cardinality) `from_cardinality` и `to_cardinality` задаёт границы
`min` и `max` числа связей; `max` отсутствует, если верхней границы нет. Ацикличность `acyclic`
по умолчанию истинна.

```yaml
relations:
  - id: 1
    name: placed_by
    from: [ORD]
    to: [CUST]
    from_cardinality: { min: 1, max: 1 }
    acyclic: true
```

**[MDL-015]** Кардинальность и ацикличность средствами схемы хранилища не выражаются и проверяются
отдельными запросами целостности (`forge checks`, `forge verify`).

### Занятые номера

**[MDL-016]** Номер поля, имя поля и код экземпляра, однажды выданные, повторно не выдаются
никогда. Номер поля живёт в выпущенных дескрипторах, код экземпляра — в документах и тикетах:
вернуть их оттуда невозможно.

**[MDL-017]** Перечень занятых номеров (Taken Numbers) пополняется инструментом при удалении
элемента. Вносить записи вручную не требуется.

```yaml
taken:
  fields: [7]
  names:  [priority]
  codes:  [19]
```

### Разряды версии

**[MDL-018]** Разряды версии (Version Components) меняются так:

| Разряд | Что меняет | Миграция | Где отражается |
|--------|------------|----------|----------------|
| MAJOR | ломающее изменение контракта | отдельный baseline | имя каталога модели |
| MINOR | структура: поля, типы, связи, перечисления | да | записывается в хранилище |
| PATCH | только описания и комментарии | нет | нигде, кроме дескриптора |

**[MDL-019]** Хеш дескриптора считается только по структурным элементам. Правка описаний его
не меняет, поэтому версия PATCH не рассогласовывает хранилище с моделью.

## Эволюция контракта

### Классы операций

**[MDL-020]** Каждая операция дельты (Delta) относится к одному из трёх классов операций
(Operation Classes): безопасная, ломающая контракт, разрушающая данные. Класс определяет
не запрет, а то, что будет напечатано при выпуске.

**[MDL-021]** Безопасные операции: добавление поля, типа узла, связи, значения перечисления;
переименование поля; ослабление кардинальности; обязательность с `required_since`. Выпускаются
молча.

**[MDL-022]** Операции, ломающие контракт: удаление элемента, сужение домена или кодомена связи,
ужесточение кардинальности, удаление значения перечисления, обязательность без `required_since`.
Выпускаются с предупреждением.

**[MDL-023]** Операции, разрушающие данные: удаление поля, типа узла, связи; смена типа поля.
Выпускаются с предупреждением, называющим удаляемые данные.

**[MDL-024]** Предупреждение не останавливает выпуск. Решение принимает владелец модели, читающий
миграцию в ревью: инструмент называет последствие, но не запрещает.

### Остановка выпуска

**[MDL-025]** Выпуск останавливают три случая, и все три — ошибка процесса, а не решение автора.
Вход завершается кодом `1`.

| Случай | Что делать |
|--------|------------|
| Содержание изменено, версия та же | повысить средний разряд версии |
| Версия ниже выпущенной | вернуть версию не ниже выпущенной |
| Номер поля или код сущности выдан повторно | взять следующий свободный номер |

**[MDL-026]** Если содержание и версия совпадают с выпущенной, выпуск завершается кодом `0`
и сообщением о том, что выпускать нечего. Повторный прогон файлов не создаёт.

### Удаление поля

**[MDL-027]** Поле удаляется удалением его записи из описания типа и повышением среднего разряда
версии. Выпуск печатает предупреждение об удалении данных и выпускает удаление колонки; номер
и имя поля инструмент сам заносит в перечень занятых.

### Ввод обязательности

**[MDL-028]** Обязательность существующего поля вводится только начиная с названной версии —
через `required_since`. Выпускается условное ограничение: записи, созданные при среднем разряде
меньше указанного, остаются валидными без значения поля.

### Ломающее изменение

**[MDL-029]** Повышение среднего разряда ломающее изменение не легализует: потребители версии
продолжают ожидать прежний контракт. Если прежний контракт выводится целиком, создаётся каталог
модели следующего старшего разряда со своей начальной миграцией, а прежний остаётся доступным
потребителям.

```text
model/<пакет>.v1/   остаётся доступной потребителям
model/<пакет>.v2/   новый контракт, своя начальная миграция
```

## Выпуск миграций

### Раскладка и именование

**[MDL-030]** Каталог миграции определяется элементом модели, который изменился, а не таблицами,
которые трогает SQL: история одного типа лежит в одном каталоге за всё время его существования.

```text
changelog/
  master.yaml          порядок применения, генерируется
  registry.yaml        реестр выпусков, генерируется
  core/                общие элементы и замыкающие миграции
  br/                  миграции типа BR
  rel/                 сигнатуры связей
```

**[MDL-031]** Имя файла миграции — метка времени вида `Version20260915142233.sql`. Оно уникально
без общего счётчика и не конфликтует при слиянии веток.

### Порядок применения

**[MDL-032]** Порядок применения задаёт `master.yaml` явными включениями: сначала общие элементы,
затем типы узлов, затем связи. Имена файлов порядок не задают — хронология выпуска не совпадает
с зависимостями элементов.

### Замыкающая миграция

**[MDL-033]** Каждая версия завершается замыкающей миграцией (Closing Migration). Она записывает
номер версии и хеш модели и несёт предусловие: в хранилище лежит хеш предыдущей версии. При
несовпадении накат останавливается до выполнения изменений схемы.

```sql
--changeset model-gen:close.1.3.0 labels:model-1.3.0
--comment: 1.2.0 -> 1.3.0
--preconditions onFail:HALT
--precondition-sql-check expectedResult:1 SELECT count(*) FROM model_state WHERE hash = 'sha256:aaa…'
UPDATE model_state SET version = '1.3.0', hash = 'sha256:bbb…';
```

**[MDL-034]** Отпечаток версии и хеша модели в хранилище меняет только замыкающая миграция, той же
транзакцией, что и схему. Поэтому отпечаток служит признаком версии модели, фактически лежащей
в хранилище.

### Неизменяемость выпущенного

**[MDL-035]** Выпущенный файл миграции не меняется ни по имени, ни по содержанию: путь входит
в опознание changeset'а, а содержание — в контрольную сумму реестра выпусков. Исправление
выпускается следующей миграцией.

**[MDL-036]** Сверка хранилища `forge verify` проверяет контрольные суммы выпущенных файлов
и называет изменённый или удалённый файл расхождением.

### Смена СУБД

**[MDL-037]** Новое хранилище получает не историю миграций, а свёртку модели (Baseline) —
`forge gen --baseline`. Переигрывать историю на новом движке не нужно: результат целиком выводится
из дескриптора. Перенос данных к контракту модели не относится.
