## APB-001 Поставка плагином

**Требования:**

1. Механизм — вход, ядро, навыки, нормы, глоссарий, образцовый шаблон — поставляется одним
   плагином Claude Code, и все его файлы лежат под корнем плагина.
2. Плагин — единственный способ поставки: вендоренная копия механизма в дереве
   проекта-потребителя не поддерживается.
3. Манифест плагина объявляет версию; версия меняется осознанной правкой манифеста, а не каждым
   коммитом репозитория-источника.
4. Репозиторий-источник объявляет маркетплейс файлом `.claude-plugin/marketplace.json` с записью
   плагина по относительному пути.
5. Репозиторий-источник грузит плагин из своего каталога на месте — локальным маркетплейсом
   источника `directory`, — а не установкой самого себя; второй копии механизма в нём нет.

**Основание:**

- платформа: файлы вне каталога плагина при установке не копируются; манифест с закреплённой
  версией держит потребителей на кешированной копии до смены строки версии; плагин, включённый
  коммитимым `.claude/settings.json`, доустанавливается сам, если источник записи маркетплейса —
  относительный путь;
- [TERM-001](../../../rules/terminology.md#единый-источник-определения) и
  [DOC-023](../../../rules/documentation-rules.md#жизненный-цикл-документа): у сведения
  один носитель, вторая копия расходится молча;
- требования эталона `plugin-delivery`: «Механизм поставляется плагином», «Распространение
  плагина».

**Воплощение в эталоне:** `.claude-plugin/marketplace.json` — источник `./plugin/backlog`;
`plugin/backlog/.claude-plugin/plugin.json` — `version`; `.claude/settings.json` —
`extraKnownMarketplaces` с источником `directory` и `enabledPlugins`.

**Отклонённые альтернативы:**

| Вариант | Причина отказа |
|---------|----------------|
| Пакет Python с console script | Требует `uv` или `pipx` на каждой машине и второй путь обновления |
| Инструмент MCP | Процесс на каждую сессию и описания инструментов в каждом ходе ради однократной записи файла |
| `git submodule` | После обычного клона подмодуль не извлечён; шаблоны внутри чужого модуля потребитель не правит |
| `git subtree` | Обновление `git subtree pull` на каждом потребителе приносит чужие коммиты в его историю; оставлен резервным путём без маркетплейса |
| Механизм в образе контейнера агента | Версия механизма становится версией чужого образа; навык в образе перекрыт монтированием каталога аккаунта; без контейнера механизма нет |
| Отдельный образ или compose-сервис механизма | Агент в контейнере не вызывает `docker`; каждое порождение стало бы задачей хоста |
| Навык и нормы в `~/.claude/` | Носитель уходит из репозитория: его не версионирует проект и не видит коллега |
| Копирование файлов по манифесту установщиком | Обновление исполняемого кода остаётся ручным прогоном при готовом механизме платформы |

**Признак соответствия:**

- `marketplace.json` содержит запись плагина с относительным путём источника;
- `plugin.json` содержит поле `version`;
- файлы механизма вне корня плагина отсутствуют; копий файлов поставки в дереве проекта нет;
- в репозитории-источнике плагин включён через локальный маркетплейс.

## APB-002 Вход командной строки

**Требования:**

1. Вход — один исполняемый файл в `bin/` плагина: он на `PATH` инструмента Bash, агент зовёт его
   по имени, разрешение навыка записывается как `Bash(<вход>:*)`.
2. Вход находит корень поставки сам — от разрешённого пути своего файла (`command -v "$0"`),
   а не от рабочего каталога и не от переменных платформы.
3. Вход один на все предметные операции и операций не знает: операция — имя шаблона в вызове.
4. Каждая работа — подкоманда входа с `--help`; эталон: `generate`, `check-template`, `lint`,
   `verify`, `norms`, `sample`.
5. Коды возврата едины для всех подкоманд — `0`, `1`, `2` по
   [архитектуре](./architecture.md#коды-возврата).
6. Корень проекта-потребителя вход берёт из `CLAUDE_PROJECT_DIR`, иначе ищет маркер `.git` вверх
   от рабочего каталога; умолчания каталогов считаются от корня проекта, а не от рабочего
   каталога.
7. Вход ничего не пишет в каталог поставки, включая кеш байт-кода.

**Основание:**

- платформа: файлы каталога `bin/` плагина находятся на `PATH` инструмента Bash, пока плагин
  включён; путь установки несёт версию и устаревает при обновлении;
- [CLAR-016](../../../rules/clean-architecture.md#слой-инфраструктуры-clar-014016): обработчик
  вызова зависит от слоя приложения, а не от домена;
- требования эталона `plugin-delivery`: «Вход вызывается командой», «Вход не зависит от своего
  места»;
- `BKL-003` эталона: механизм порождения один на все операции, шаблон — свой у каждой.

**Воплощение в эталоне:** `plugin/backlog/bin/backlog` — POSIX sh: `SELF=$(command -v "$0")`,
`ROOT=$(dirname "$SELF")/..`, `PYTHONPATH="$ROOT/src"`, `PYTHONDONTWRITEBYTECODE=1`,
`exec python3 -m backlog "$@"`; `plugin/backlog/src/backlog/__main__.py` — `argparse`
с подпарсерами, `EXIT_OK`/`EXIT_BLOCKED`/`EXIT_ENVIRONMENT`, `_project_root()`.

**Отклонённые альтернативы:**

| Вариант | Причина отказа |
|---------|----------------|
| Вызов по пути `sh <путь>/backlog.sh` | Путь установки несёт версию и устаревает при первом обновлении |
| Отдельная команда на каждую операцию | Вход пришлось бы править при заведении каждой операции |
| Умолчания каталогов от рабочего каталога | Прогон из подкаталога заводит второй каталог следа |

**Признак соответствия:**

- `<вход> --help` и `<вход> <подкоманда> --help` завершаются кодом `0`;
- прогон одной и той же подкоманды из корня проекта и из его подкаталога даёт один и тот же
  адрес артефакта;
- после прогонов входа в корне плагина нет новых файлов;
- коды возврата подкоманд совпадают с таблицей кодов.

## APB-003 Ядро без зависимостей

**Требования:**

1. Ядро обходится стандартной библиотекой интерпретатора.
2. Файл зависимостей существует и пуст; появившаяся зависимость записывается пином точной версии.
3. Окружение интерпретатора собирается, только если зависимости объявлены, и лежит вне корня
   плагина: `${CLAUDE_PLUGIN_DATA}`, иначе пользовательский кеш.
4. Окружение несёт метку — версию интерпретатора и способ сборки — и пересобирается при их смене;
   способы сборки перебираются в фиксированном порядке, исчерпание перечня даёт диагностику
   с кодом `2`.

**Основание:**

- критерий поставки эталона: не утяжелять зависимость, ни индекса пакетов, ни `uv`, ни `pipx`;
- платформа: `${CLAUDE_PLUGIN_ROOT}` меняется при обновлении плагина, состояние в нём не хранится;
- порождение и рендер не должны менять поведение от обновления библиотеки — отсюда пины.

**Воплощение в эталоне:** `plugin/backlog/src/requirements.txt` — пуст с комментарием-обоснованием;
`plugin/backlog/lib/python-env.sh` — `prepare_python_env`, перебор `uv` → `venv` → `venv-target`,
метка `.env-mark`; `plugin/backlog/bin/backlog` — сборка только при непустом файле зависимостей.

**Отклонённые альтернативы:**

| Вариант | Причина отказа |
|---------|----------------|
| Зависимости, вендоренные в поставку | Поставка растёт и несёт чужой код без пина интерпретатора |
| Окружение внутри корня плагина | Обновление плагина его стирает |
| Установка зависимостей в системный интерпретатор | Меняет машину пользователя ради инструмента |

**Признак соответствия:**

- импорты ядра — только модули стандартной библиотеки и самого пакета;
- каждая строка файла зависимостей — комментарий либо пин `==`;
- путь окружения не лежит под корнем плагина.

## APB-004 Слои ядра

**Требования:**

1. Ядро разделено на домен, слой приложения и инфраструктуру; зависимости направлены внутрь.
2. Домен содержит агрегат порождённого артефакта, контракт записи и правила «чем артефакт обязан
   быть» — функции над разобранной структурой; о формате файла, грамматике шаблона и файловой
   системе домен не знает.
3. Сценарий слоя приложения — компонент с единственной публичной операцией `execute`, принимающей
   неизменяемый входной контракт и возвращающей неизменяемый выходной; контракты логики не несут.
4. Сценарий получает зависимости через конструктор и зависит только от контрактов, а не от
   реализаций; каждому сценарию соответствует контракт сценария, от которого зависит вызывающий.
5. Сценарий вместе со своими входным и выходным контрактами образует одну единицу группировки.
6. Инфраструктура содержит грамматику шаблона, рендер, разбор артефакта, файловые адаптеры
   и чтение файлов поставки; бизнес-правил в ней нет.
7. Вход ядра — внешний обработчик и точка сборки: создаёт адаптеры, собирает сценарий, переводит
   выходной контракт в текст и код возврата.
8. Правило структуры артефакта существует в одном экземпляре — в домене — и вызывается всеми
   сценариями, которым нужно.

**Основание:** [CLAR-001](../../../rules/clean-architecture.md#слои-и-направление-зависимостей-clar-001),
[CLAR-002](../../../rules/clean-architecture.md#слой-домена-clar-002004-clar-006),
[CLAR-004](../../../rules/clean-architecture.md#слой-домена-clar-002004-clar-006),
[CLAR-006](../../../rules/clean-architecture.md#слой-домена-clar-002004-clar-006),
[CLAR-007..013](../../../rules/clean-architecture.md#слой-приложения-clar-007013),
[CLAR-015](../../../rules/clean-architecture.md#слой-инфраструктуры-clar-014016),
[CLAR-016](../../../rules/clean-architecture.md#слой-инфраструктуры-clar-014016),
[CLAR-021](../../../rules/clean-architecture.md#solid-clar-017021). Модульная организация
[CLAR-022](../../../rules/clean-architecture.md#модульная-организация-clar-022023) в эталоне
вырождена: предмет один, модуль один.

**Воплощение в эталоне:** `plugin/backlog/src/backlog/domain.py` — `Backlog` (frozen),
`BacklogRepository`, `structure_findings`, `execution_findings`;
`plugin/backlog/src/backlog/application/` — файл на сценарий (`generate_backlog.py`,
`check_template.py`, `lint_backlog.py`, `verify_backlog.py`) и `contracts.py`;
`plugin/backlog/src/backlog/infrastructure.py` — `render`, `template_grammar`, `MarkdownBacklog`,
`FileTemplates`, `FileBacklogs`, `DeliveryFiles`; `plugin/backlog/src/backlog/__main__.py` — сборка
сценариев. Отступления эталона от требований 4 и 7 — в [отклонениях](./deviations.md).

**Отклонённые альтернативы:**

| Вариант | Причина отказа |
|---------|----------------|
| Плоский скрипт без слоёв | Правило структуры нужно порождению, приёмке и двум проверкам — у него было бы четыре носителя |
| Правила структуры в инфраструктуре рядом с разбором | Смешивает «как записано» с «чем обязано быть»: смена формата ломала бы правила |
| Исключения вместо исходов сценария | Повторное порождение — штатный ответ, а не ошибка; исключение заставило бы вход различать штатное и аварийное по типу |

**Признак соответствия:**

- домен импортирует только стандартную библиотеку;
- слой приложения импортирует только домен и стандартную библиотеку;
- инфраструктура не импортирует вход ядра; никто, кроме точки запуска, не импортирует вход ядра;
- входные и выходные контракты неизменяемы (`frozen`) и методов логики не несут;
- у каждого сценария ровно одна публичная операция `execute`.

## APB-005 Разделение чтения и записи

**Требования:**

1. Контракт записи артефактов объявлен в домене и содержит только заведение артефакта целиком;
   операций чтения и перезаписи в нём нет.
2. Контракты чтения объявлены в слое приложения и узки: каждый отвечает на один вопрос — источник
   шаблона, наличие и адрес артефакта, текст артефакта, разбор текста.
3. Сценарий-команда зависит от контракта записи и нужных ему контрактов чтения; сценарии-запросы —
   только от контрактов чтения.
4. Реализации контракта записи и контрактов чтения — отдельные компоненты инфраструктуры.

**Основание:** [CQRS-001..006](../../../rules/cqrs.md#подробное-описание),
[CLAR-020](../../../rules/clean-architecture.md#solid-clar-017021) — узкие контракты.

**Воплощение в эталоне:** `BacklogRepository.add` в `domain.py`; `TemplateSource`,
`BacklogLookup`, `BacklogSource`, `DocumentParser` в `application/contracts.py`;
`GenerateBacklogUseCase` — команда, `CheckTemplateUseCase`, `LintBacklogUseCase`,
`VerifyBacklogUseCase` — запросы. Требование 4 эталон нарушает: `FileBacklogs` реализует
и запись, и чтение наличия — см. [отклонения](./deviations.md#apb-d03-одна-реализация-записи-и-чтения).

**Отклонённые альтернативы:**

| Вариант | Причина отказа |
|---------|----------------|
| Один контракт репозитория с чтением и записью | Сценарию-запросу стала бы доступна запись; проверка могла бы «исправить» найденное |
| Операция «правь задачу» в контракте записи | Отметки ставит исполнение, а не механизм порождения: порождённое задним числом не правится |

**Признак соответствия:**

- в контракте записи нет операций чтения и перезаписи;
- конструкторы сценариев-запросов не принимают контракт записи;
- контракты чтения объявлены в слое приложения, а не в домене.

## APB-006 Доменная модель

**Требования:**

1. Порождённый артефакт — неизменяемый агрегат; его идентичность — адрес, пара «операция
   и предмет».
2. Ход исполнения — отметки и дописанные значения — правит файл, а не агрегат: состав артефакта
   остаётся тем, каким его дал шаблон.
3. Исходы сценариев и контракта записи — значения (`written`/`exists`,
   `generated`/`already-generated`/`rejected`), а не исключения.
4. Расхождение проверки — объект-значение с местом (строкой файла) и сообщением.
5. Имена компонентов кода совпадают с понятиями норм и глоссария поставки.

**Основание:** [DDD-001](../../../rules/ddd.md#единый-язык-ddd-001002),
[DDD-006](../../../rules/ddd.md#агрегат-ddd-006009),
[DDD-010](../../../rules/ddd.md#сущность-ddd-010011),
[DDD-012..014](../../../rules/ddd.md#value-object-ddd-012014),
[DDD-020..022](../../../rules/ddd.md#repository-ddd-020022); `BKL-004` эталона — порождённое
не правится.

**Воплощение в эталоне:** `Backlog` с `address`, `Finding`, `Leftover`, `BacklogTask`,
`BacklogDocument` — `dataclasses.dataclass(frozen=True)`; константы `BACKLOG_WRITTEN`,
`BACKLOG_EXISTS`, `GENERATED`, `ALREADY_GENERATED`, `REJECTED`, `ACCEPTED`, `DEFECTIVE`.

**Отклонённые альтернативы:**

| Вариант | Причина отказа |
|---------|----------------|
| Изменяемый агрегат с операциями отметки | Механизм порождения получил бы право переписывать состоявшийся файл |
| Ошибка на повторное порождение | Владелец, повторивший вызов, получает отказ вместо пути к своему артефакту |

**Признак соответствия:**

- классы агрегата, объектов-значений и контрактов неизменяемы;
- повторный вызов порождения с тем же адресом завершается кодом `0` и не меняет файл;
- каждое расхождение проверки называет строку файла.

## APB-007 Нормы как данные поставки

**Требования:**

1. Нормы предмета с кодами `{ПРЕФИКС}-NNN` и глоссарий их понятий лежат только в поставке.
2. В дерево проекта-потребителя поставка их не копирует и точек подключения проекта не правит.
3. Внешнему вызову вход выдаёт нормы текстом: все нормы с глоссарием, одно правило по коду
   (раздел от заголовка, содержащего абзац `**[КОД]**`), образцовый шаблон; неизвестный код —
   код возврата `2`.
4. Навыки адресуют нормы путём от `${CLAUDE_PLUGIN_ROOT}`.
5. Шаблоны, артефакты и навыки называют норму кодом и вызовом выдачи — «`КОД` (`<вход> norms --rule КОД`)»,
   — не пересказывая её и не называя адрес файла норм.
6. Репозиторий-источник подключает нормы и глоссарий в контекст агента `@`-импортом из каталога
   поставки, без копий.

**Основание:** [TERM-001](../../../rules/terminology.md#единый-источник-определения),
[DOC-023](../../../rules/documentation-rules.md#жизненный-цикл-документа); `BKL-008` эталона —
норма называется кодом и вызовом; требования эталона `norms-delivery`.

**Воплощение в эталоне:** `plugin/backlog/share/rules/operation-backlog-rules.md`,
`plugin/backlog/share/docs/glossary.md`, `plugin/backlog/templates/sample-operation.md`;
`DeliveryFiles` и `rule_section` в `infrastructure.py`; подкоманды `norms`, `norms --rule`,
`sample`; `@plugin/backlog/share/...` в `CLAUDE.md` эталона.

**Отклонённые альтернативы:**

| Вариант | Причина отказа |
|---------|----------------|
| Установочный прогон копий норм в проект с манифестом хешей | Две копии норм и ручной прогон обновления; в эталоне был и упразднён |
| `@`-импорт норм из каталога установки плагина | Путь несёт версию и устаревает; внешний импорт требует одобрения |
| Пересказ нормы в навыке или шаблоне | Молчаливое расхождение при первой правке правила |

**Признак соответствия:**

- в дереве проекта-потребителя нет файлов норм и глоссария плагина;
- `<вход> norms --rule <существующий код>` печатает раздел правила и завершается кодом `0`;
- `<вход> norms --rule <несуществующий код>` завершается кодом `2`;
- в навыках и образце нормы названы кодом, ссылки ведут от `${CLAUDE_PLUGIN_ROOT}`.

## APB-008 Навыки и разделение ролей

**Требования:**

1. Детерминированная работа — порождение, приёмка, проверки, выдача норм — выполняется входом;
   работа, требующая суждения агента или диалога с владельцем, — навыком.
2. Порядок исполнения артефактов существует в одном носителе — навыке исполнения — и не
   воспроизводится ни в шаблонах, ни в артефактах.
3. Порождённый артефакт несёт указатель носителя порядка (значение `runner` во фронтматтере —
   имя навыка `/<плагин>:<навык>`), а его первая задача предписывает загрузить носитель.
4. Навык приёмки ведёт от вопроса «нужен ли артефакт операции» к шаблону, принятому прогоном;
   шаблон пишет вызывающий.
5. Навык не порождает артефакт и не правит его состав.
6. Фронтматтер навыка: `name`, `description` с условием применения, узкий `allowed-tools`
   (`Bash(<вход>:*)` и необходимый минимум).
7. Тело навыка: границы навыка, порядок шагов, таблица исходов, таблица версий.

**Основание:** [CLAR-017](../../../rules/clean-architecture.md#solid-clar-017021) — одна причина
меняться; `BKL-008` эталона — передача исполнения называет носитель и предписывает его загрузку;
требования эталона `operation-backlog` «Носитель порядка исполнения» и `template-acceptance`
«Навык приёмки шаблона», «Шаблон пишет вызывающий».

**Воплощение в эталоне:** `plugin/backlog/skills/backlog-run/SKILL.md` — пять шагов исполнения,
стоп-знак, таблица исходов; `plugin/backlog/skills/backlog-template/SKILL.md` — шесть шагов
приёмки, таблица исходов; переменная `BACKLOG_RUNNER` с умолчанием `/backlog:backlog-run`.

**Отклонённые альтернативы:**

| Вариант | Причина отказа |
|---------|----------------|
| Порядок исполнения в каждом шаблоне | Несколько носителей одного правила |
| Исполнение артефакта входом | Вход не судит о состоянии и не спрашивает владельца |
| Ссылка на навык вместо указателя с загрузкой | Ссылка в тексте не загружает: исполнение без порядка оставляет задачи неотмеченными |

**Признак соответствия:**

- у каждого навыка заполнены `name`, `description`, `allowed-tools`;
- образцовый шаблон после порождения несёт `runner`, и первая задача называет его значение;
- шаги исполнения отсутствуют в шаблонах и образце.

## APB-009 Конвейер артефакта

**Требования:**

1. Шаблон начинается маркером версии `<!-- template_version: X.Y.Z -->`; шаблон без маркера —
   ошибка окружения; маркер снимается при рендере, версия попадает во фронтматтер артефакта.
2. Грамматика шаблона: подстановка `{{имя}}`, условный блок `{{#признак}}…{{/признак}}`, обратный
   блок `{{^признак}}…{{/^признак}}`; вызов называет **все** признаки — взведённые и снятые.
3. Пропуск условного блока виден в артефакте: обратный блок оставляет названное решение
   об отсутствии группы задач.
4. Значения, которые порождение выводит само (дата, штамп, предмет, версия шаблона, указатель
   носителя порядка), перечислены в одном месте, общем для порождения и приёмки.
5. Порождённый текст проходит структурную проверку **до** записи файла; при расхождении файл
   не заводится, код `2`, перечень расхождений и указание править шаблон.
6. Единственный результат успешного порождения — файл артефакта; порождение иного состояния
   не меняет.
7. Артефакт несёт: фронтматтер значений исполнения; задачи с отметкой `- [ ]`, строкой проверки
   и признаком «выполнено ранее»; стоп-знак у необратимых задач; каркас — коды норм исполнения,
   первая задача — загрузка носителя порядка, вторая — структурная проверка артефакта; таблицу
   версий в конце.
8. Порождённый артефакт по составу не правится; ход исполнения — отметки и значения,
   дописываемые во фронтматтер.
9. Исполнение: при расхождении отметки с признаком верно состояние; повторный проход состояния
   не меняет; прерванное исполнение продолжается с первой невыполненной задачи; задача
   со стоп-знаком исполняется после подтверждения, запрошенного непосредственно перед ней;
   по завершении — проверка полноты исполнения.

**Основание:** `BKL-003`..`BKL-007`, `BKL-010` эталона; требования эталона `operation-backlog`;
[DOC-022](../../../rules/documentation-rules.md#жизненный-цикл-документа) — таблица версий;
[CLAR-013](../../../rules/clean-architecture.md#слой-приложения-clar-007013) — сценарий задаёт
порядок шагов, правила остаются домену.

**Воплощение в эталоне:** `TEMPLATE_VERSION_PATTERN`, `load_template`, `render`, `scalar`
в `infrastructure.py`; `_derived_values` в `__main__.py`; `GenerateBacklogUseCase`;
`EXECUTION_NORM_CODES`, `SELF_CHECK_CALL` в `domain.py`; образец `templates/sample-operation.md`.

**Отклонённые альтернативы:**

| Вариант | Причина отказа |
|---------|----------------|
| Версия шаблона константой кода | Версия носителя хранилась бы вне носителя и расходилась при правке |
| Проверка после записи файла | Лежащий артефакт правке не подлежит — исправить дефект было бы нечем |
| Неназванный признак как «снят» по умолчанию | Забытый признак молча выбрасывает группу задач |
| Повторный сбор значений при исполнении | Расхождение между подтверждённым и выполненным |

**Признак соответствия:**

- шаблон без маркера версии — код `2`, файла нет;
- шаблон, оставляющий подстановку без значения, — код `2`, файла нет;
- порождение, не назвавшее признак условного блока, — код `2`, файла нет;
- повторное порождение по тому же адресу — код `0`, файл неизменен;
- порождённый образец проходит структурную проверку с кодом `0`.

## APB-010 Приёмка шаблона перебором

**Требования:**

1. Подкоманда приёмки прогоняет шаблон по каждому сочетанию признаков условных блоков —
   `2ⁿ` вариантов — тем же путём, что порождение до записи: рендер, разбор, структурная проверка.
2. Значения приёмки: выводимые — тем же способом, что при порождении; прочие подстановки —
   заглушка с именем подстановки; файл артефакта не пишется.
3. Каждое расхождение названо с сочетанием признаков; последняя строка вывода — вердикт: число
   вариантов и число расхождений.
4. Перебор ограничен пределом числа признаков; сверх предела — код `2` и совет разделить шаблон.
5. Изменение шаблона не считается завершённым без приёмки с кодом `0`; при правке версия
   в маркере выше той, что была до правки, — сверка с прочитанной до правки строкой, а не
   с историей системы контроля версий.

**Основание:** `BKL-009`, `BKL-004` эталона; требования эталона `template-acceptance`;
[GIT-019](../../../rules/git-rules.md#чтение-истории) — история не читается без указания.

**Воплощение в эталоне:** `CheckTemplateUseCase`, `MAX_FLAGS = 8` в
`application/check_template.py`; `_check_values`, `_stub` в `__main__.py`; шаг 2 и шаг 5 навыка
`backlog-template`.

**Отклонённые альтернативы:**

| Вариант | Причина отказа |
|---------|----------------|
| Проверка шаблона одним порождением | Проверяет один вариант: дефект ветки снятого признака доходит до исполнителя |
| Неограниченный перебор | Время растёт как `2ⁿ`; шаблон с многими признаками стоит разделить |

**Признак соответствия:**

- шаблон с дефектом только в ветке снятого признака — код `1`, расхождение названо с этим
  сочетанием;
- шаблон сверх предела признаков — код `2`;
- после приёмки в каталоге следа нет новых файлов.

## APB-011 Адресация артефактов

**Требования:**

1. Артефакт лежит по адресу `<каталог следа>/<операция>/<предмет>/<имя файла>`; операция
   и предмет проверяются как допустимые сегменты пути.
2. Предмет повторяемой операции — штамп прогона `YYYYMMDDHHMMSS` по умолчанию; предмет
   однократной операции — предмет предметной области, названный вызовом.
3. Каталог следа и каталог шаблонов — значения вызова: ключ, иначе переменная окружения,
   иначе каталог в корне проекта.
4. Перечень игнорируемых путей проекта поставка не правит; заводя каталог следа впервые,
   вход печатает рекомендацию строки для него.
5. Лежащий артефакт остаётся на своём адресе и после исполнения.

**Основание:** `BKL-002` эталона; платформа — состояние не пишется в корень плагина;
[DOCK-009](../../../rules/docker.md#переменные-окружения-dock-004-dock-009-dock-010) по аналогии —
значения окружения, а не вшитые константы.

**Воплощение в эталоне:** `FileBacklogs.path_of` — `<root>/<operation>/<subject>/tasks.md`;
ключи `--root`, `--templates`, переменные `BACKLOG_ROOT`, `BACKLOG_TEMPLATES`; `_segment`,
`_default_dir`, `IGNORE_ADVICE` в `__main__.py`.

**Отклонённые альтернативы:**

| Вариант | Причина отказа |
|---------|----------------|
| Отказ по занятому адресу у повторяемой операции | Повторное утверждение владельца нечем исполнить |
| Вшитый путь каталога следа | Каталог принадлежит применяющему, а не механизму |
| Дописывание строки в `.gitignore` | Перечень принадлежит проекту; закрывающая строка скрыла бы прежнее содержимое |

**Признак соответствия:**

- порождение без предмета даёт предмет вида `YYYYMMDDHHMMSS`;
- ключ и переменная окружения переносят каталог следа;
- `.gitignore` проекта после первого порождения не изменён, рекомендация напечатана.

## APB-012 Проверка прогоном

**Требования:**

1. Артефакт проверяется прогоном, а не чтением: структурная проверка — по лежащему файлу,
   проверка полноты исполнения — по завершении исполнения и включает структурную.
2. Проверка перечисляет все расхождения за один прогон, каждое — с местом в файле; последняя
   строка — вердикт.
3. Проверка расхождение называет, но не правит.
4. Ядро и вход покрыты тестами на средствах стандартной библиотеки; тесты лежат в
   репозитории-источнике и в поставку не входят.
5. Поведение плагина описано требованиями OpenSpec по возможностям: поставка, выдача норм,
   артефакт, приёмка шаблона, проверка.
6. Код несёт обоснование решений в документирующих строках модулей и классов: не «что делает»,
   а «почему так».

**Основание:** `BKL-010` эталона;
[MAKE-004](../../../rules/makefile-rules.md#локальный-прогон-проверки-make-004) по аналогии —
изменение не завершено без локального прогона проверки;
[DOC-020](../../../rules/documentation-rules.md#полнота-содержания) — ограничения фиксируются явно.

**Воплощение в эталоне:** подкоманды `lint` и `verify`; `structure_findings`,
`execution_findings` в `domain.py`; `tests/test_backlog.py` — `python3 -m unittest discover -s tests`,
72 проверки на 2026-10-13; `openspec/specs/backlog/{plugin-delivery,norms-delivery,operation-backlog,template-acceptance,backlog-lint}/spec.md`.

**Отклонённые альтернативы:**

| Вариант | Причина отказа |
|---------|----------------|
| Остановка на первом расхождении | Исправление дефектного шаблона шло бы по одному нарушению за прогон |
| Автоматическое исправление найденного | Проверка не видит состояния: отметка по домыслу утверждает неподтверждённое исполнение |
| Тестовый фреймворк сторонней библиотеки | Нарушает [APB-003](#apb-003-ядро-без-зависимостей) для репозитория-источника без выигрыша |

**Признак соответствия:**

- тесты прогоняются одной командой без установки зависимостей и завершаются успехом;
- проверка файла с несколькими дефектами называет их все;
- после проверки файл артефакта не изменён;
- требования OpenSpec проходят `openspec validate --strict`.
