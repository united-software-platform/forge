# Образец плагина агента

Техническая спецификация архитектурного образца, по которому проект строит собственный плагин
агента: поставка, вход командной строки, ядро в слоях, навыки и конвейер «шаблон → порождение →
проверка → исполнение». Документ экспортируемый: он переносится в целевой проект и читается там.

## Назначение и границы

Образец плагина агента (Agent Plugin Blueprint, APB) — техническое решение без принадлежности
к предметной области. Он описывает, **как** устроен плагин, а не **о чём** он: предмет —
порождаемые артефакты, их нормы и шаблоны — каждый проект вносит свой.

Эталонная реализация APB — плагин `backlog` проекта `formular`: механизм порождения
и исполнения беклогов операций. Эталон назван по путям и понятиям в
[эталонной реализации](./reference-implementation.md) и служит иллюстрацией, а не источником
требований: требования сформулированы здесь, ролями образца.

В спецификацию **входит**:

- поставка плагином, вход командной строки, ядро и его окружение;
- разбивка ядра на слои и применение правил Clean Architecture, CQRS и DDD;
- навыки агента и разделение ролей между входом и навыками;
- конвейер артефакта, приёмка шаблона, адресация и проверка прогоном.

В спецификацию **не входит**:

- окружение разработки — контейнер агента, `Makefile`, раннер хоста: его поставляет
  SDD Developer Kit, и в целевом проекте оно уже есть;
- правила `rules/*` — они лежат в целевом проекте, и спецификация называет их кодами
  (`CLAR-003`, `CQRS-001`, `DDD-009`), не пересказывая;
- предмет эталона — понятия беклога и предмет его шаблонов: он упомянут только как
  [след применения](./reference-implementation.md#след-предмета).

## Как читать спецификацию

Основной читатель — агент, приводящий целевой проект к образцу. Порядок работы:

1. Прочитать [понятия образца](#понятия-образца) и [классификацию](#классификация): они
   задают, к какому классу приложения образец применим.
2. Прочитать [архитектуру](./architecture.md): компоненты, слои, поток артефакта.
3. Прочитать [решения](./decisions.md) `APB-001`..`APB-012`: каждое несёт основание,
   воплощение в эталоне, отклонённые альтернативы и признак соответствия.
4. Свериться с [отклонениями эталона](./deviations.md): эталон их не образец.
5. Пройти [чек-лист соответствия](./conformance.md) и выдать отчёт в его форме.

Требование спецификации сформулировано **свойством**, а не стеком: Python, POSIX sh,
`unittest` и Markdown — воплощение эталона. Целевой проект вправе выбрать другой язык, если
свойство и его признак соответствия сохраняются.

> **Важно:** правила, на которые ссылается спецификация, — правила целевого проекта. При
> расхождении требования APB с правилом проекта верно правило, а расхождение фиксируется
> отчётом соответствия, а не молчаливым выбором.

## Понятия образца

Понятия определены здесь и только здесь; прочие файлы спецификации ими оперируют.

| Понятие | Определение |
|---------|-------------|
| Плагин (Plugin) | Единица поставки механизма агенту: манифест, вход, ядро, навыки, нормы и образец под одним корнем |
| Репозиторий-источник (Source Repository) | Репозиторий, в котором плагин разрабатывается и из которого распространяется |
| Проект-потребитель (Consumer Project) | Проект, в котором плагин установлен и применяется |
| Вход (Entry Point) | Единственная команда командной строки плагина; подкомандами порождает, принимает шаблон, проверяет и выдаёт нормы |
| Ядро (Core) | Код, исполняемый входом: домен, слой приложения и инфраструктура |
| Предметная операция (Subject Operation) | Вид работы, для которой плагин порождает артефакт; у каждой — свой шаблон |
| Шаблон (Template) | Файл проекта-потребителя, описывающий состав артефакта одной предметной операции: подстановки, условные блоки, текст задач; несёт свою версию первой строкой |
| Порождённый артефакт (Generated Artifact) | Файл, порождённый входом по шаблону и значениям вызова; по составу не правится |
| Каталог следа (Trace Directory) | Каталог проекта-потребителя, в котором лежат порождённые артефакты |
| Нормы (Norms) | Правила предмета плагина с кодами `{ПРЕФИКС}-NNN` и глоссарий их понятий; лежат только в поставке |
| Навык исполнения (Execution Skill) | Навык плагина, несущий единственный порядок исполнения порождённых артефактов |
| Навык приёмки (Acceptance Skill) | Навык плагина, ведущий от вопроса «нужен ли артефакт» к шаблону, принятому прогоном |
| Признак исполнения (Completion Marker) | Состояние, по которому задача артефакта признаётся выполненной ранее; при расхождении с отметкой верно состояние |
| Стоп-знак (Stop Sign) | Пометка задачи, необратимой для внешних ссылок или публичного состояния: исполняется только после подтверждения владельца, запрошенного непосредственно перед ней |
| Владелец (Owner) | Человек, от имени которого агент исполняет артефакт и у которого запрашивает подтверждения |

> **Примечание:** признак исполнения и стоп-знак совпадают по смыслу с одноимёнными понятиями
> глоссария эталона. Спецификация определяет их у себя, потому что глоссарий эталона лежит
> в поставке плагина `backlog` и в целевой проект не переносится.

## Классификация

| Ось | Значение |
|-----|----------|
| Тип приложения | Инструмент разработки: плагин агента с входом командной строки |
| Исполнитель | LLM-агент в сеансе Claude Code; человек — владелец подтверждений |
| Среда исполнения | Локальный процесс без сервера и без фонового демона |
| Состояние | Файловое: Markdown с фронтматтером в дереве проекта-потребителя; базы данных нет |
| Поставка | Маркетплейс плагинов Claude Code, версия закреплена в манифесте |
| Зависимости | Ноль: ядро на стандартной библиотеке интерпретатора |
| Архитектурный стиль | Clean Architecture + CQRS + DDD внутри одного модуля |
| Модель работы | Порождение артефактов по шаблону и проверка прогоном |
| Взаимодействие | Синхронный вызов командной строки; сетевых обращений нет |

Образец применим к приложению, совпадающему с классификацией по осям «Тип», «Исполнитель»,
«Среда исполнения» и «Модель работы». Отличие по остальным осям допускается и фиксируется
отчётом соответствия.

## Допущения, ограничения и риски

**Допущения:**

- спецификация переносится в целевой проект по тому же пути `docs/spec/agent-plugin-blueprint/`,
  а правила лежат в `rules/` корня проекта: ссылки на правила относительны и иначе не разрешатся;
- в целевом проекте есть правила `rules/*` с кодами `DOC`, `TERM`, `CLAR`, `CQRS`, `DDD`, `GIT`
  в редакции, совпадающей по номерам с редакцией `formular` на 2026-10-13;
- целевой плагин исполняется в сеансе Claude Code: навыки, маркетплейс, переменные
  `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}` и `CLAUDE_PROJECT_DIR` — свойства этой
  платформы.

**Ограничения:**

- в claude.ai и Cowork вход недоступен: команды из каталога `bin/` плагина там не попадают
  на `PATH`;
- имя входа известно только внутри сеанса Claude Code; в обычном терминале оно не разрешается;
- признак исполнения описан прозой и прогоном не сверяется: сверка — обязанность навыка
  исполнения.

**Риски:**

- правила целевого проекта могут разойтись с редакцией, на которую ссылается спецификация:
  тогда код правила указывает на другое содержание. Отчёт соответствия называет такие коды;
- эталон меняется независимо от спецификации: пути эталона, названные текстом, могут
  устареть. Требования от этого не зависят — они сформулированы ролями.
