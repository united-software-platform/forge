# Правила Docker и Docker Compose

Правила описания сервисов проекта в Docker Compose: именование, сеть, переменные окружения,
параметры сервиса, инициализация состояния в томах, пользователь контейнера и публикация портов.

## Имя файла конфигурации [DOCK-011]

**[DOCK-011]** Файл конфигурации Docker Compose именуется строго `docker-compose.yaml` и располагается
в корне проекта. Краткие формы (`compose.yaml`, `compose.yml`, `docker-compose.yml`) не используются.

---

## Префикс имён [DOCK-001..002]

**[DOCK-001]** Каждое имя сервиса начинается с префикса проекта. Префикс образуется от имени проекта
и приводится к короткой форме в нижнем регистре (kebab-case).

```text
Проект «Интернет-магазин» → префикс shop → сервисы shop-app, shop-db, shop-proxy
```

Префикс фиксируется один раз и далее не меняется: он отличает контейнеры проекта от контейнеров
соседних проектов на той же машине. Имя проекта берётся из того источника, который проект считает
своим именем; выводить префикс из содержимого произвольного документа не требуется.

**[DOCK-002]** Имя контейнера (`container_name`) совпадает с именем сервиса. Это убирает
автогенерируемый суффикс Compose (`<project>-<service>-1`) и делает имя предсказуемым.

```yaml
services:
  shop-db:
    container_name: shop-db
```

---

## Сеть [DOCK-003]

**[DOCK-003]** В `docker-compose.yaml` обязательно объявляется сеть в секции `networks`, и каждый
сервис подключается к ней явно. Имя сети — с префиксом проекта.

```yaml
networks:
  shop-net:
    driver: bridge
```

---

## Переменные окружения [DOCK-004, DOCK-009, DOCK-010]

**[DOCK-004]** Атрибут `env_file` **запрещён**. Переменные передаются через секцию `environment`
с интерполяцией.

**[DOCK-009]** Все значения секции `environment` берутся из файла `.env` через `${VAR}`. Compose
автоматически читает `.env` из каталога проекта для подстановки значений — хардкод значений
в `docker-compose.yaml` запрещён.

```yaml
    environment:
      DB_NAME: ${DB_NAME}
      DB_USER: ${DB_USER}
      DB_PASSWORD: ${DB_PASSWORD}
```

**[DOCK-010]** Рядом с `.env` создаётся `.env.example` — коммитимый шаблон со всеми переменными
и несекретными значениями по умолчанию. Сам `.env` игнорируется git.

> **Внимание:** `.env` содержит реальные значения и не коммитится; `.env.example` — единственный
> версионируемый файл переменных.

## Параметры сервиса [DOCK-005, DOCK-006, DOCK-007]

**[DOCK-005]** `working_dir` указывается там, где это осмысленно — прежде всего для контейнера
приложения (рабочий каталог приложения).

**[DOCK-006]** `healthcheck` добавляется там, где готовность сервиса критична для зависящих
сервисов — прежде всего для хранилищ данных, очередей и любых сервисов, к которым обращаются
при старте.

**[DOCK-007]** Для всех **долгоживущих** сервисов задаётся `restart: unless-stopped`. Единственное
исключение — сервисы инициализации состояния (см. [DOCK-014](#сервис-инициализации-состояния-dock-014-dock-015)):
они выполняют задачу и завершаются, поэтому политика перезапуска у них `restart: "no"`.

---

## Сервис инициализации состояния [DOCK-014, DOCK-015]

**[DOCK-014]** Если сервису для работы требуется **состояние внутри тома**, которого нет
в образе — модели, словари, расширения, схемы, справочники, — это состояние наполняется
**одноразовым сервисом инициализации** `{сервис}-init`. Наполнять том вручную (командами внутри
работающего контейнера) запрещено: том — не декларация, ручное наполнение не воспроизводится
и теряется при пересоздании тома.

Требования к init-сервису:

- имя — `{имя целевого сервиса}-init`, `container_name` совпадает с ним (DOCK-002);
- образ — тот же, что у целевого сервиса (в нём уже есть нужный клиент), либо минимальный образ
  с необходимым инструментом;
- монтирует тот же том, что и целевой сервис;
- источник значений — переменные `.env` (DOCK-009), а не литералы в команде;
- `restart: "no"` — исключение из DOCK-007: сервис обязан завершиться, а не перезапускаться;
- подключается к общей сети (DOCK-003), портов не публикует.

**[DOCK-015]** Порядок запуска задаётся `depends_on`:

- init-сервис ждёт готовности целевого сервиса — `condition: service_healthy` (целевому сервису
  при этом нужен `healthcheck`, DOCK-006);
- все потребители инициализированного состояния ждут **успешного завершения** init-сервиса —
  `condition: service_completed_successfully`.

Без `service_completed_successfully` потребитель стартует раньше, чем состояние наполнено, и падает
на первом обращении либо молча работает на пустом хранилище.

```yaml
  shop-search:
    image: ${SEARCH_IMAGE}
    container_name: shop-search
    restart: unless-stopped
    volumes:
      - shop-search-data:/var/lib/search        # состояние живёт в томе
    healthcheck:                                # нужен для service_healthy [DOCK-006]
      test: ["CMD-SHELL", "search-cli status >/dev/null 2>&1"]
      interval: 10s
      timeout: 5s
      retries: 5
    networks:
      - shop-net

  shop-search-init:                             # одноразовое наполнение тома [DOCK-014]
    image: ${SEARCH_IMAGE}
    container_name: shop-search-init
    restart: "no"                               # исключение из DOCK-007
    environment:
      SEARCH_HOST: shop-search:9200
      INDEX_SCHEMA: ${SEARCH_INDEX_SCHEMA}      # значения из .env [DOCK-009]
      DICTIONARY: ${SEARCH_DICTIONARY}
    entrypoint: ["/bin/sh", "-c"]
    command: ['search-cli schema apply "$$INDEX_SCHEMA" && search-cli dict load "$$DICTIONARY"']
    depends_on:
      shop-search:
        condition: service_healthy              # ждёт готовности целевого сервиса [DOCK-015]
    networks:
      - shop-net

  shop-app:
    # ...
    depends_on:
      shop-search-init:
        condition: service_completed_successfully # ждёт наполнения состояния [DOCK-015]
```

> **Внимание:** в `command` переменные экранируются двойным `$$` — иначе Compose подставит их сам
> на этапе интерполяции и внутрь контейнера уйдёт уже раскрытое (или пустое) значение.

## Пользователь контейнера приложения [DOCK-012, DOCK-013]

**[DOCK-012]** Контейнер приложения запускается не от `root`, а под выделенным непривилегированным
пользователем. Пользователь и группа создаются в `Dockerfile`, процесс приложения исполняется
от их имени (`USER` в `Dockerfile` и/или `user:` в сервисе Compose). Имя пользователя выбирает
проект — важно, что это не `root`.

**[DOCK-013]** Рабочий каталог (`working_dir`) и все внутренние файлы контейнера приложения
принадлежат этому пользователю. Владелец задаётся при копировании файлов (`COPY --chown`) и/или
через `chown -R` рабочего каталога. Файлы приложения не должны оставаться во владении `root`:
процесс, не владеющий своими файлами, не сможет писать туда, куда должен, а процесс, запущенный
от `root`, получает права, которые ему не нужны.

```dockerfile
# Базовый образ выбирает проект — это язык и среда выполнения приложения
ARG APP_BASE_IMAGE
FROM ${APP_BASE_IMAGE}

# Выделенные непривилегированные пользователь и группа [DOCK-012]
RUN groupadd -g 1000 app \
    && useradd -u 1000 -g app -m -s /bin/sh app

WORKDIR /srv/app

# Все внутренние файлы принадлежат пользователю приложения [DOCK-013]
COPY --chown=app:app . /srv/app
RUN chown -R app:app /srv/app

# Процесс приложения исполняется от непривилегированного пользователя [DOCK-012]
USER app
```

## Порты [DOCK-008]

**[DOCK-008]** Порты, опубликованные на хост, **не назначаются по умолчанию** (`5432:5432`, `80:80`
и т.п.): порт по умолчанию занят первым же соседним проектом, использующим ту же СУБД. Хостовый порт
выбирается из диапазона, закреплённого за проектом. Диапазон проект задаёт сам и фиксирует
в документации — важно, что он выбран осознанно и не пересекается с диапазонами соседних проектов.

Внутренний порт контейнера остаётся штатным; меняется только хостовая (левая) часть маппинга:

```yaml
    ports:
      - "${DB_PORT}:5432"   # хостовый порт из диапазона проекта, контейнерный штатный
```

По возможности перед назначением проверяется, свободен ли порт на хосте:

```bash
for p in 11080 11432 11672; do
  ss -ltn | grep -q ":$p " && echo "$p занят" || echo "$p свободен"
done
```

## Пример

`.env.example` (рядом — `.env` с реальными значениями, игнорируется git):

```bash
DB_NAME=shop
DB_USER=shop
DB_PASSWORD=change_me
APP_HTTP_PORT=11080
DB_PORT=11432
```

`docker-compose.yaml`:

```yaml
services:
  shop-app:
    build:
      context: .
      dockerfile: docker/app/Dockerfile
    container_name: shop-app
    working_dir: /srv/app
    user: app
    restart: unless-stopped
    environment:
      DATABASE_URL: ${DATABASE_URL}
    depends_on:
      shop-db:
        condition: service_healthy
    networks:
      - shop-net

  shop-db:
    image: ${DB_IMAGE}
    container_name: shop-db
    restart: unless-stopped
    environment:
      POSTGRES_DB: ${DB_NAME}
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    ports:
      - "${DB_PORT}:5432"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER} -d ${DB_NAME}"]
      interval: 10s
      timeout: 5s
      retries: 5
    networks:
      - shop-net

  shop-proxy:
    image: ${PROXY_IMAGE}
    container_name: shop-proxy
    restart: unless-stopped
    depends_on:
      - shop-app
    ports:
      - "${APP_HTTP_PORT}:80"
    networks:
      - shop-net

networks:
  shop-net:
    driver: bridge
```
