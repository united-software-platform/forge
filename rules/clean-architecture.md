## Слои и направление зависимостей [CLAR-001]

**[CLAR-001]** Зависимости направлены **строго внутрь**: инфраструктура знает о приложении,
приложение знает о домене, домен не знает ни о чём. Внутренний слой не ссылается на внешний
ни прямо, ни через посредника.

```text
┌─────────────────────────────────┐
│         Инфраструктура          │  фреймворк, хранилище, транспорт, очереди
│  ┌───────────────────────────┐  │
│  │        Приложение         │  │  сценарии использования, входные и выходные контракты
│  │  ┌─────────────────────┐  │  │
│  │  │         Домен       │  │  │  сущности, значения, доменные события,
│  │  │                     │  │  │  доменные сервисы, контракты репозиториев
│  │  └─────────────────────┘  │  │
│  └───────────────────────────┘  │
└─────────────────────────────────┘
```

Слой — логическая группа, а не каталог. Как она воплощена физически — каталогом, пакетом, модулем,
пространством имён или отдельным исполняемым сервисом, — определяет проект. Правило проверяется
по направлению зависимости между компонентами, а не по совпадению путей с примером.

## Слой домена [CLAR-002..004, CLAR-006]

Домен содержит **бизнес-правила**: инварианты, расчёты, правила перехода между состояниями.

**[CLAR-002]** Состав слоя:

- **Сущность** — бизнес-объект с идентичностью;
- **Объект-значение** — объект без идентичности, неизменяемый;
- **Доменное событие** — свершившийся факт домена, только данные;
- **Доменный сервис** — операция над несколькими сущностями, не принадлежащая ни одной из них;
- **Контракт репозитория** — описание доступа к данным; реализация живёт в инфраструктуре.

**[CLAR-003]** Операции сохранения в контракте репозитория принимают **доменную модель целиком**.
Передавать вместо неё набор отдельных значений, транспортную структуру или произвольный набор полей
запрещено: репозиторий, принимающий части, теряет возможность проверить целостность сохраняемого.

```text
// Запрещено — репозиторий принимает разрозненные значения
Repository OrderRepository:
    update(id: OrderId, status: string, total: int): void

// Правильно — репозиторий принимает модель целиком
Repository OrderRepository:
    update(order: Order): void
```

**Запрещено в домене:**

- **[CLAR-004]** Зависимости от фреймворка, библиотеки доступа к данным, контейнера внедрения
  зависимостей, транспорта и любых других внешних механизмов. Домен должен собираться и проверяться
  тестами без запуска приложения.
- **[CLAR-006]** Контракты и сервисы, реализация которых обязана обратиться к инфраструктуре —
  к хранилищу, очереди, внешней службе. Такой контракт принадлежит слою приложения: домен объявляет
  только то, что выполнимо в его собственных терминах.

## Слой приложения [CLAR-007..013]

Слой приложения содержит **правила приложения**: порядок шагов операции, обращение к контрактам,
объявление контрактов тех служб, реализация которых уходит в инфраструктуру.

**[CLAR-007]** Каждая бизнес-операция — отдельный сценарий использования. Один сценарий —
одно действие.

### Состав сценария использования

| Роль | Суффикс имени | Назначение |
|------|---------------|------------|
| Реализация | `UseCase` | Выполняет операцию |
| Контракт | `UseCaseInterface` | То, от чего зависит вызывающая сторона |
| Входной контракт | `Input` | Неизменяемый набор данных на вход |
| Выходной контракт | `Output` | Неизменяемый набор данных на выход; если возвращать нечего — отсутствует |

Суффикс фиксирует роль компонента, а не способ её выражения в языке. Если в языке нет отдельного
понятия контракта, роль выражается принятым в нём средством — важна возможность подменить реализацию,
а не ключевое слово.

### Правила сценария использования

- **[CLAR-008]** У сценария ровно одна публичная операция — `execute`. Она принимает входной контракт
  и возвращает выходной либо не возвращает ничего. Вторая публичная операция означает, что сценариев
  на самом деле два.
- **[CLAR-009]** Входной и выходной контракты неизменяемы: после создания их поля не меняются.
  Логики они не содержат — ни проверок, ни расчётов, ни обращений к другим компонентам.
- **[CLAR-010]** Сценарий зависит только от **контрактов домена**, не от конкретных реализаций.
- **[CLAR-011]** Сценарий вместе со своими входным и выходным контрактами образует отдельную единицу
  группировки. Как она выражена — каталогом, пакетом или пространством имён — решает проект;
  важно, что части одного сценария лежат вместе, а не растворяются в общих каталогах по типам.

**Запрещено в слое приложения:**

- **[CLAR-012]** Прямое обращение к хранилищу, транспорту и внешним службам — только через контракты,
  реализация которых остаётся в инфраструктуре.
- **[CLAR-013]** Бизнес-логика: инварианты и расчёты принадлежат домену. Слой приложения решает,
  **в каком порядке** вызвать доменные операции, но не **что** они означают.

## Слой инфраструктуры [CLAR-014..016]

Слой инфраструктуры содержит детали реализации:

- реализации контрактов репозиториев;
- обработчики входящих запросов — принимают запрос, вызывают сценарий использования, возвращают ответ;
- отображение доменной модели на схему хранения;
- клиенты внешних служб, очередей, файловой системы.

**[CLAR-014]** Реализация репозитория сохраняет ровно **один агрегат**. Всё, что нужно для сохранения
и не принадлежит этому агрегату — сгенерированные значения, коды, идентификаторы из внешних
систем, — приходит в репозиторий готовым аргументом от сценария использования, а не добывается
репозиторием самостоятельно.

**Запрещено в слое инфраструктуры:**

- **[CLAR-015]** Бизнес-логика.
- **[CLAR-016]** Прямая зависимость обработчика входящего запроса от доменных объектов в обход слоя
  приложения.

## SOLID [CLAR-017..021]

| ID | Принцип | Правило |
|----|---------|---------|
| **CLAR-017** | **SRP** — единственная ответственность | У компонента ровно одна причина меняться. Обработчик обрабатывает ровно одну операцию. |
| **CLAR-018** | **OCP** — открытость/закрытость | Новое поведение добавляется новым компонентом, а не правкой существующего. |
| **CLAR-019** | **LSP** — подстановка Лисков | Реализация полностью соблюдает контракт: не сужает область допустимых входов, не возвращает неожиданных ошибок, не игнорирует параметры. |
| **CLAR-020** | **ISP** — разделение контрактов | Контракты узкие и сфокусированные: контракт репозитория пользователей не содержит операций над заказами. |
| **CLAR-021** | **DIP** — инверсия зависимостей | Внешние слои зависят от абстракций, объявленных в домене. Конкретные реализации подставляются инфраструктурой при сборке приложения. |

## Модульная организация [CLAR-022..023]

**[CLAR-022]** Код группируется по **доменным модулям**, а не по техническим слоям. Верхний уровень
разбиения отвечает на вопрос «о чём этот код», а не «какого он типа».

```text
// Запрещено — верхний уровень разбиения технический
Домен          → сущности всех модулей вперемешку
Приложение     → сценарии всех модулей вперемешку
Инфраструктура → реализации всех модулей вперемешку

// Правильно — верхний уровень разбиения доменный
Заказы    → домен, приложение, инфраструктура заказов
Платежи   → домен, приложение, инфраструктура платежей
Каталог   → домен, приложение, инфраструктура каталога
```

Слои при этом не исчезают: они существуют внутри каждого модуля, и направление зависимостей
[CLAR-001](#слои-и-направление-зависимостей-clar-001) действует внутри модуля без изменений.

**[CLAR-023]** Модуль — самостоятельная граница контекста. Межмодульные зависимости идут только
через контракты домена: модуль «Платежи» не обращается к внутренним компонентам модуля «Заказы»
напрямую.

## Пример

Операция «подтвердить заказ» в трёх слоях.

```text
// ДОМЕН — контракт репозитория
Repository OrderRepository:
    findById(id: OrderId): Order        // отсутствие заказа — ошибка домена
    save(order: Order): void            // принимает модель целиком [CLAR-003]

// ДОМЕН — сущность, в ней живёт бизнес-правило
Entity Order:
    id: OrderId
    status: OrderStatus

    confirm(confirmedBy: UserId): void
        if this.status != OrderStatus.DRAFT:
            throw OrderAlreadyConfirmed(this.id)
        this.status = OrderStatus.CONFIRMED
        this.confirmedBy = confirmedBy

// ПРИЛОЖЕНИЕ — входной контракт: неизменяемый, без логики [CLAR-009]
Input ConfirmOrderInput:
    orderId: string
    confirmedBy: string

// ПРИЛОЖЕНИЕ — контракт сценария
Contract ConfirmOrderUseCaseInterface:
    execute(input: ConfirmOrderInput): void

// ПРИЛОЖЕНИЕ — сценарий: порядок шагов, но не бизнес-правила [CLAR-013]
UseCase ConfirmOrderUseCase implements ConfirmOrderUseCaseInterface:
    constructor(orders: OrderRepository)    // зависит от контракта домена [CLAR-010]

    execute(input: ConfirmOrderInput): void
        order = this.orders.findById(OrderId(input.orderId))
        order.confirm(UserId(input.confirmedBy))   // правило проверяет сущность
        this.orders.save(order)

// ИНФРАСТРУКТУРА — реализация контракта домена
Implementation StoredOrderRepository implements OrderRepository:
    constructor(storage: StorageClient)     // деталь реализации остаётся здесь

    findById(id: OrderId): Order
        record = this.storage.read("orders", id.value)
        if record is empty:
            throw OrderNotFound(id)
        return OrderMapper.toDomain(record)

    save(order: Order): void
        this.storage.write("orders", OrderMapper.toRecord(order))

// ИНФРАСТРУКТУРА — обработчик запроса: зависит от контракта приложения [CLAR-016]
Handler ConfirmOrderHandler:
    constructor(useCase: ConfirmOrderUseCaseInterface)

    handle(request): Response
        this.useCase.execute(ConfirmOrderInput(
            orderId     = request.param("orderId"),
            confirmedBy = request.currentUserId()
        ))
        return Response.noContent()
```
