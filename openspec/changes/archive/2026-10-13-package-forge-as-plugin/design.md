# Design: поставка forge плагином Claude Code

## Context

Мотивация — в `proposal.md`, раздел Why. Состояние до change зафиксировано в
`docs/reports/apb-conformance-baseline.md`.

Что важно для подхода:

- **Ядро** — пакет `forge_model`: `cli.py`, плоские модули предмета, подпакеты `gen/` и `intent/`.
  Он собирается hatchling из `tools/forge_model`, вход — консольный скрипт `forge-model`.
- **Зависимости:** `yaml` импортируется в пяти модулях, `psycopg` — лениво в `_verify`
  (`cli.py:160`).
- **Пути по умолчанию** — константы `DEFAULT_*` относительно рабочего каталога (`cli.py:22-25`).
- **Коды возврата:**
  - `main` отображает `ModelError` в `1`. Под `ModelError` идут и отказ модели, и ошибки процесса
    цикла: `engine.py:50`, `engine.py:114`.
  - Незамкнутый цикл возвращает `CYCLE_OPEN = 2`.
  - Исключение `psycopg` при подключении не перехватывается.
- **Окружение разработки:** `uv` и `pyproject.toml` с extra `dev`. Пайплайны вызывают
  `uv run … python -m forge_model` с `PYTHONPATH=tools`.
- **Образец:** спецификация APB в `docs/spec/agent-plugin-blueprint/`. Утверждённые отклонения
  перечислены в базовом отчёте, раздел «Применимость образца».

## Goals / Non-Goals

**Goals:**

- forge подключается в проект-потребитель только включением плагина и работает из любого
  его подкаталога;
- поведение подкоманд `build`, `diff`, `gen`, `checks`, `verify`, `intent run` сохраняется,
  меняются только коды возврата по таблице APB;
- разработка и тесты в репозитории-источнике идут на том же коде, что уходит в поставку.

**Non-Goals:**

- раскладка ядра по слоям и контракты сценариев — change `layer-forge-core`;
- отказ от `pyyaml` и `psycopg`;
- конвейер «шаблон → порождение» и приёмка шаблона перебором (APB-009, APB-010);
- публикация плагина во внешний маркетплейс: change даёт запись маркетплейса в репозитории,
  а распространение вне него — отдельное решение.

## Decisions

### D1. Раскладка поставки

```text
.claude-plugin/marketplace.json          запись маркетплейса: forge → ./plugin/forge
.claude/settings.json                    extraKnownMarketplaces (directory) + enabledPlugins
plugin/forge/
  .claude-plugin/plugin.json             name, version 0.1.0, description
  bin/forge                              вход, POSIX sh
  lib/python-env.sh                      сборка окружения, метка
  src/requirements.txt                   пины ==
  src/forge_model/                       перенесённый пакет
  skills/model-change/SKILL.md
  skills/model-release/SKILL.md
  share/rules/model-rules.md             нормы MDL-NNN
  share/docs/glossary.md
  templates/sample-model/                образец минимальной модели
```

Пакет переносится через `git mv` из `tools/forge_model/` в `plugin/forge/src/forge_model/`
без изменения внутренних импортов. Это сохраняет историю файлов и не смешивает перенос
с перекладкой по слоям.

Начальная версия `0.1.0` берётся из `pyproject.toml`. Так у пакета и у плагина один номер,
и `pyproject.toml` читает его же — через `[tool.hatch.version]` из `plugin.json` либо явной
правкой обоих файлов при подъёме.

Альтернатива — оставить пакет в `tools/` и сослаться на него из плагина. Отвергнута: механизм
вне корня плагина не попадает в кеш установки (APB-001 (1)).

### D2. Вход и окружение

`bin/forge` делает следующее:

1. Находит себя через `command -v "$0"` и вычисляет `ROOT`.
2. Подключает `lib/python-env.sh`. Если в `requirements.txt` есть пины, функция
   `prepare_python_env` собирает окружение в `${CLAUDE_PLUGIN_DATA:-${XDG_CACHE_HOME:-$HOME/.cache}/forge-plugin}/env`.
3. Выставляет `PYTHONPATH="$ROOT/src"` и `PYTHONDONTWRITEBYTECODE=1`.
4. Выполняет `exec "$PY" -m forge_model "$@"`.

Метка `.env-mark` содержит версию интерпретатора, способ сборки и sha256 файла `requirements.txt`.
Если метка не совпала, окружение пересобирается. Способы перебираются в порядке
`uv venv` + `uv pip install`, затем `python3 -m venv` + `pip install`. Если оба способа
исчерпаны, вход печатает диагностику и завершается кодом `2`.

Вариант `venv-target` из эталона не берётся: `psycopg[binary]` ставит бинарные колёса,
и установка через `--target` без изоляции интерпретатора ненадёжна. Отличие фиксируется
в приёмочном отчёте.

Альтернатива — `uv run --with` при каждом вызове. Отвергнута: сетевое разрешение зависимостей
на каждом вызове и отсутствие метки.

### D3. Корень проекта и каталоги

В `cli.py` появляется функция `_project_root()`. Корень проекта берётся из `CLAUDE_PROJECT_DIR`,
иначе ищется `.git` вверх от `Path.cwd()`. Если не найдено ни то, ни другое — `ModelError`
окружения, код `2`.

Умолчания `DEFAULT_*` становятся относительными путями, которые разрешаются от корня проекта
в момент разбора аргументов. Порядок приоритета для каждого каталога: ключ, затем переменная
окружения, затем умолчание.

| Каталог | Ключ | Переменная | Умолчание |
|---------|------|------------|-----------|
| Модель | `--model` | `FORGE_MODEL_DIR` | `model/forge.reqs.v1` |
| Выпуски | `--releases` | `FORGE_RELEASES_DIR` | `model/releases` |
| Миграции | `--changelog` | `FORGE_CHANGELOG_DIR` | `changelog` |
| Отчёты цикла | `--runs` | `FORGE_RUNS_DIR` | `model/intents/runs` |

Явно переданный относительный путь в ключе разрешается от рабочего каталога, как принято
у командной строки. От корня проекта считаются только умолчания (APB-002 (6)).

Рекомендация `.gitignore` печатается в `_intent_run`, когда каталог отчётов создан этим прогоном
и не найден в `.gitignore` корня проекта простым сравнением строк.

### D4. Коды возврата

Вводятся константы `EXIT_OK = 0`, `EXIT_REJECTED = 1`, `EXIT_ENVIRONMENT = 2`. Разделение
`ModelError` на две ветки делается без перекладки ядра: появляется подкласс
`EnvironmentFault(ModelError)`, и `main` отображает его в `2`.

| Ситуация | Сейчас | Станет |
|----------|--------|--------|
| Модель отвергнута, гейт, расхождения `verify` | `1` | `1` |
| Незамкнутый цикл: останов, лимит | `2` | `1` |
| Ошибка процесса цикла: `engine.py:50`, `engine.py:114` | `1` | `2` |
| Ошибка аргументов (`argparse`) | `2` | `2` |
| Корень проекта не найден, нет файла, хранилище недоступно | трассировка или `1` | `2` |

Ошибку процесса цикла отличает от отказа модели место возникновения: `_intent_run` перехватывает
`ModelError` движка и поднимает `EnvironmentFault`. Ошибка подключения `psycopg.OperationalError`
в `_verify` тоже переводится в `EnvironmentFault`.

Альтернатива — оставить `CYCLE_OPEN = 2`. Отвергнута: APB-002 (5) требует одной таблицы
на все подкоманды, а спека `intent-pipeline` требует только различия кодов, и новая таблица
это различие сохраняет.

### D5. Нормы и образец

Нормативные положения `docs/model-format.md`, `docs/model-evolution.md` и `docs/migrations.md`
переносятся в `share/rules/model-rules.md` и нумеруются `MDL-001`… по порядку разделов:
формат, эволюция, миграции. Каждое правило — абзац `**[MDL-NNN]**` под заголовком раздела.

Понятия модели переходят в `share/docs/glossary.md` в формате TERM-004:
- тип узла, поле, сигнатура связи;
- занятые номера;
- разряды версии;
- дескриптор, дельта, классы операций;
- замыкающая миграция.

`docs/model-*.md` и `docs/migrations.md` сжимаются до пользовательского описания со ссылками
на нормы по DOC-023. Нормы для них остаются данными поставки. Поскольку в проекте-потребителе
этих документов нет, ссылки ведут на вызов `forge norms --rule`, а относительная ссылка
на файл поставки действует только в репозитории-источнике.

`forge norms --rule КОД` выделяет раздел от заголовка, под которым стоит абзац `**[КОД]**`,
до следующего заголовка того же или более высокого уровня. Это функция инфраструктуры чтения
файла поставки.

`forge sample` печатает файлы `templates/sample-model/` с разделителями-путями. Образец собирается
из фикстуры `tests/fixtures/model/forge.reqs.v1`, урезанной до одного типа узла. Тест проверяет,
что образец проходит `build`.

Альтернатива — нормы в `CLAUDE.md` проекта-потребителя через установщик. Отвергнута APB-007:
появились бы две копии и ручное обновление.

### D6. Навыки

- **`skills/model-change/SKILL.md`** — шаги:
  1. Нужно ли изменение?
  2. Нормы: `forge norms --rule …`.
  3. Правка модели вызывающим.
  4. `forge build`.
  5. `forge diff` и разбор классов операций.
  6. Решение владельца по ломающим и разрушающим операциям.

  `allowed-tools`: `Bash(forge:*)`, `Read`, `Edit`.
- **`skills/model-release/SKILL.md`** — шаги:
  1. Состояние: есть ли дескриптор версии и запись реестра.
  2. `forge diff`.
  3. Стоп-знак: подтверждение владельца с версией и дельтой.
  4. `forge gen`.
  5. `forge verify`, если хранилище названо.
  6. Итог.

  `allowed-tools`: `Bash(forge:*)`, `Read`.

Цикл `intent run` навыка не получает: это детерминированный прогон по сценарию, и его вызывает
вход. Раздел «Команды» в `docs/migrations.md` заменяется ссылкой на навык `forge:model-release`:
порядок выпуска живёт в одном носителе.

### D7. Разработка, тесты и CI

`pyproject.toml`:
- `packages = ["plugin/forge/src/forge_model"]`;
- `pythonpath = ["plugin/forge/src", "."]`;
- `mypy_path = ["plugin/forge/src", "tools/host-runner"]`;
- `files = ["plugin/forge/src", "tools", "tests"]`.

Консольный скрипт `forge-model` остаётся для разработки. Пины `pyyaml` и `psycopg[binary]`
в `requirements.txt` совпадают с версиями из `uv.lock`. В `dependencies` проекта стоят те же
пины, а тест сверяет оба файла.

Пайплайны:
- `model.yml` вызывает `plugin/forge/bin/forge diff` вместо `python -m forge_model diff`;
- `tests.yml` без изменений состава;
- `quality.yml` получает шаг `openspec validate --all --strict`. Он относится к качеству
  репозитория, а не к тестам, поэтому одна проверка остаётся в одном пайплайне.

Тест «прогон без установки зависимостей» (APB-012 (4)) выполняется по-разному. В CI его даёт
`uv run --extra dev pytest`. Для автора — та же одна команда: `uv` ставит окружение сам,
ручной установки нет. Отличие от эталона на `unittest` фиксируется в приёмочном отчёте.

### D8. Подключение в репозитории-источнике и `CLAUDE.md`

`.claude/settings.json` (коммитимый):
- `extraKnownMarketplaces.forge-local = {source: {source: "directory", path: "."}}`;
- `enabledPlugins = {"forge@forge-local": true}`.

`.claude/settings.local.json` остаётся вне git.

В `CLAUDE.md` в разделе «Правила кода» добавляются `@plugin/forge/share/rules/model-rules.md`
и `@plugin/forge/share/docs/glossary.md`. Файл записан в `.sdd-kit-manifest.json`, поэтому
следующая переустановка kit'а покажет расхождение хеша. Это локальное отличие называется
в приёмочном отчёте и в строке версий `CLAUDE.md`. `AGENTS.md` получает те же ссылки, если он
дублирует подключение правил.

## Risks / Trade-offs

- **Смена кодов возврата ломает внешних вызывающих.** → Отмечено как BREAKING в proposal.
  Внутри репозитория вызывающих двое: `model.yml` и тесты, обновляются в этом change.
- **Окружение собирается при первом вызове и требует сети.** → Сборка однократна и закреплена
  меткой. Без сети вход даёт код `2` с диагностикой, а не трассировку.
- **Переустановка kit'а затрёт `@`-импорт в `CLAUDE.md`.** → Отличие названо в отчёте и в таблице
  версий файла. Устойчивое решение — точка расширения `CLAUDE.md` в kit'е, вне этого change.
- **Нормы `MDL` сразу после переноса могут разойтись с поведением кода.** → Перенос не меняет
  смысла положений. Расхождения, найденные при нумерации, записываются в приёмочный отчёт,
  а не исправляются молча.
- **Плагин доступен только в Claude Code.** В claude.ai и Cowork `bin/` не на `PATH`. →
  Ограничение APB, принятое владельцем. Для разработки остаётся `forge-model`.
- **Ядро без слоёв остаётся несоответствием APB-004..006.** → Долг явно перенесён в change
  `layer-forge-core`, а приёмочный отчёт сохраняет исход «Не соответствует».

## Migration Plan

1. Перенос пакета и правка конфигурации: тесты зелёные на новом пути до любых изменений поведения.
2. Вход, окружение, корень проекта, коды возврата: тесты обновлены вместе с кодом.
3. Нормы, глоссарий, образец, подкоманды `norms` и `sample`.
4. Навыки, маркетплейс, `settings.json`, `CLAUDE.md`.
5. Документация, `README.md`, пайплайны, строгая проверка спецификаций.
6. Приёмочный отчёт.

Откат — возврат ветки. В `main` change попадает одним слиянием, и данные модели
проекта-потребителя он не меняет.
