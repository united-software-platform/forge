# Design: раскладка ядра forge по слоям

## Context

Причины и состав — в `proposal.md`, требования — в `specs/core-architecture/spec.md`
и дельте `specs/model-contract/spec.md`.

Исходное состояние ядра `plugin/forge/src/forge_model/` — 3142 строки в плоских модулях:

| Модуль | Что смешано |
|--------|-------------|
| `model.py` (490) | чтение файлов, разбор YAML, формат значений, объекты модели |
| `validate.py` | правила структуры; первое нарушение поднимает `ModelError` |
| `descriptor.py` | компиляция модели в `dict[str, Any]`, хеш, сериализация JSON |
| `diff.py` | дельта и классы операций над словарями дескрипторов |
| `release.py` | гейт совместимости (`GateError`), поиск выпущенного дескриптора на диске, запись `_taken.yaml` |
| `registry.py` | чтение и запись реестра в одном модуле |
| `gen/` | операции схемы, диалект PostgreSQL, раскладка каталога и запись файлов |
| `checks.py`, `verify.py` | правила целостности и SQL-запросы вместе |
| `intent/` | движок с внедряемыми шагами; чтение сценария и запись отчётов внутри движка |
| `delivery.py` | чтение файлов поставки |
| `cli.py` | разбор ключей и сборка выпуска: порядок шагов, пересборка дескриптора, запись дескриптора и реестра |

Тесты: 200, из них тесты входа и сквозные — эталон поведения. Модульные тесты импортируют
внутренние пути `forge_model.*` напрямую.

Ограничения:

- выпущенные дескрипторы и миграции живут в проектах-потребителях, поэтому байты дескриптора,
  хеш и содержимое миграций не должны измениться;
- зависимости `pyyaml` и `psycopg` остаются (утверждённое отклонение APB-003);
- mypy `strict`, ruff и `MAKE`-нормы действуют без послаблений.

## Goals / Non-Goals

**Goals:**

- признаки соответствия APB-004..006 проверяются тестами архитектуры, а не чтением кода;
- отклонения эталона D01–D05 не повторяются;
- раскладка идёт по модулю за раз, и после каждого шага весь набор тестов зелёный.

**Non-Goals:**

- новые подкоманды, ключи и форматы файлов;
- второй диалект СУБД — контракт диалекта его допускает, но не добавляет;
- решения по расхождениям норм с ядром Р1–Р6: правила ядра переносятся как есть, вместе
  с расхождениями;
- пакет внедрения зависимостей: сборка — обычный код во входе.

## Decisions

### D1. Доменные модули

Верхний уровень пакета — доменные модули по CLAR-022. Технические слои живут внутри модулей.

```text
plugin/forge/src/forge_model/
  __main__.py              точка запуска
  cli.py                   вход ядра: ключи, обработчики, перевод исхода в текст и код
  assembly.py              точка сборки: адаптеры → сценарии
  errors.py                EnvironmentFault — ошибка окружения или вызова, код 2
  contract/                контракт модели: модель, правила структуры, дескриптор, дельта, гейт
  release/                 выпуск: агрегат выпуска, шаги миграции, раскладка, реестр
  store/                   хранилище: сверка схемы, правила целостности
  intent/                  цикл намерения: стадии, машина состояний, отчёты
  delivery/                файлы поставки: нормы, глоссарий, образец
```

Внутри модуля:

```text
<модуль>/
  domain.py                сущности, объекты-значения, агрегаты, правила, контракт записи
  application/
    contracts.py           контракты чтения и служб, модели чтения слоя приложения
    <сценарий>.py          UseCaseInterface, UseCase, Input, Output — одна единица (CLAR-011)
  infrastructure.py        адаптеры; при росте — пакет infrastructure/ с файлом на адаптер
```

Межмодульные зависимости идут только к `contract/domain.py` (CLAR-023): модули `release`,
`store` и `intent` получают дескриптор как объект домена контракта.

**Альтернатива — один модуль, как в эталоне.** Отклонена: у forge пять предметов с разными
нормами, а эталон вырожден, потому что у него предмет один. Плоский домен на 1500 строк
вернул бы смешение «о чём код».

**Альтернатива — слои верхним уровнем (`domain/`, `application/`, `infrastructure/`).**
Отклонена по CLAR-022.

### D2. Сценарии и их контракты

| Модуль | Сценарий | Вид | Зависимости |
|--------|----------|-----|-------------|
| `contract` | `BuildModel` | запрос | `ModelSource` |
| `contract` | `DiffModel` | запрос | `ModelSource`, `ReleasedDescriptors` |
| `release` | `ReleaseModel` | команда | `ModelSource`, `ReleasedDescriptors`, `MigrationDialect`, `Clock`, `ReleaseRepository` |
| `release` | `ReleaseBaseline` | команда | `ModelSource`, `MigrationDialect`, `Clock`, `ReleaseRepository` |
| `store` | `ListChecks` | запрос | `ModelSource`, `IntegrityQueries` |
| `store` | `VerifyStore` | запрос | `ModelSource`, `RegistryEntries`, `SchemaInspector`, `IntegrityQueries`, `IntegrityProbe` |
| `intent` | `RunIntent` | команда | `ScenarioSource`, `StepsFactory`, `RunHistory`, `RunReports` |
| `delivery` | `ShowNorms` | запрос | `DeliveryFiles` |
| `delivery` | `ShowSample` | запрос | `DeliveryFiles` |

Форма каждого сценария:

- `…UseCaseInterface` — `typing.Protocol` с одной операцией `execute(input) -> output`;
- `…UseCase` — реализация, зависимости приходят через конструктор;
- `…Input` и `…Output` — `@dataclass(frozen=True, slots=True)` без методов.

Выходной контракт несёт исход-константу модуля (`BUILT`, `RELEASED`, `NOTHING_TO_RELEASE`,
`REJECTED` и т. д.), сводку для печати и кортеж `Discrepancy(place, message)` слоя приложения.
Сценарий переводит в `Discrepancy` доменные `Finding`, `SchemaDrift` и `IntegrityViolation`
(закрывает D05). Общего `Discrepancy` на все модули нет: слой приложения одного модуля
не импортирует слой приложения другого. Каждый модуль объявляет свою модель расхождения
в своём `contracts.py`. Форма у них одна, и тест архитектуры сверяет набор полей.

Вход зависит только от `…UseCaseInterface`, реализацию подставляет `assembly.py` (закрывает D01).

**Альтернатива — абстрактные базовые классы вместо `Protocol`.** Отклонена: реализации пришлось
бы наследовать контракт, а тестовые подмены — тоже. `Protocol` проверяется mypy структурно,
и при этом каждая реализация явно называет контракт в документирующей строке и в аннотации
фабрики сборки.

### D3. Вход и точка сборки

`cli.py` сохраняет разбор ключей, разрешение каталогов (`_project_root`, переменные
`FORGE_*_DIR`) и таблицу кодов возврата. Обработчик подкоманды:

1. строит `…Input` из ключей;
2. получает сценарий из фабрики `assembly.py` по каталогам;
3. печатает выходной контракт;
4. возвращает код по исходу.

`assembly.py` — единственное место, где создаются адаптеры инфраструктуры. Тест входа
подменяет фабрику и проверяет, что обработчик работает с любой реализацией контракта.

`EnvironmentFault` остаётся исключением с кодом `2`: это ошибка окружения или вызова, а не
исход. `ModelError` и `GateError` исчезают — их место занимают исходы `REJECTED` с перечнем
расхождений.

### D4. Чтение модели и правило структуры

Ответственность делится на три части:

- **Инфраструктура `YamlModelSource`** читает файлы через `yaml.compose` и берёт номер строки
  из меток узлов. Ошибки формата копятся, а не поднимаются: синтаксис YAML, неизвестный или
  отсутствующий ключ, значение не того вида. Результат — `ModelReading(model | None, findings)`.
  Модель собирается, если формат позволил построить объекты; значения при этом могут нарушать
  правила.
- **Домен `contract`** держит объекты модели. У каждого элемента есть `Place(file, line)`.
  Правило структуры `structure_findings(model) -> tuple[Finding, ...]` существует в единственном
  экземпляре и собирает все нарушения:
  - формы кодов и имён по `MDL-005`, `MDL-006`, `MDL-010`;
  - уникальность номеров;
  - пересечение с занятыми номерами;
  - ссылки на типы и перечисления.
- **Сценарии** всех подкоманд, собирающих модель, вызывают один доменный сервис
  `compile_descriptor(model) -> Compiled(descriptor | None, findings)`. Правило структуры
  вызывается внутри него, поэтому обойти его нельзя (APB-004 (8)).

Регулярные выражения переезжают из `model.py` в домен как есть, вместе с расхождением Р6.

**Альтернатива — проверять форму значений при разборе, как сейчас.** Отклонена: так смешиваются
«как записано» и «чем обязано быть», и правило кода типа имело бы два носителя.

### D5. Дескриптор как объект домена

`Descriptor` — `@dataclass(frozen=True)` с полями `model`, `version`, `major`, `hash`,
`enums`, `types`, `relations`, `taken`. Элементы — кортежи объектов-значений.

- `Descriptor.hash` считается в домене от канонической формы структурных элементов (`MDL-019`).
  Каноническая форма — функция домена над стандартными `json` и `hashlib`: она часть
  контракта хеша, а не формат хранения.
- Запись `model/releases/<версия>.json` и чтение выпущенных дескрипторов — в инфраструктуре.
  Обе стороны используют ту же каноническую форму, поэтому байты файла совпадают с прежними.
- Дельта `diff(old, new) -> Delta` работает над объектами дескрипторов, а не над словарями.

Эталон байтов (D11) фиксирует дескриптор до раскладки.

### D6. Выпуск: агрегат, гейт и запись

Разделение по слоям:

- **Домен `release`:**
  - `CompatibilityGate.decide(current, previous) -> GateDecision` с исходами «выпускать»,
    «выпускать нечего», «отвергнуто» и перечнем `Finding`;
  - `MigrationStep` — нейтральный шаг схемы, бывший `gen.ops.Operation`;
  - правила раскладки по `MDL-030..032`: каталог шага по элементу модели, имя
    `VersionYYYYMMDDHHMMSS.sql`, порядок включений;
  - `Release` — агрегат выпуска: версия, дескриптор с пополненным перечнем занятых номеров,
    кортеж `Migration(folder, name, text)`, порядок применения, запись реестра с контрольными
    суммами, добавленные занятые номера;
  - контракт записи `ReleaseRepository.add(release) -> RELEASE_WRITTEN | RELEASE_EXISTS`.
- **Слой приложения `release`:**
  - `MigrationDialect` — рендер шага, замыкающая миграция, свёртка;
  - `Clock` — источник метки времени;
  - `ReleasedDescriptors` — последний выпущенный дескриптор старшего разряда.
- **Инфраструктура `release`:**
  - `PostgresDialect`;
  - `FileReleaseRepository` — запись: файлы миграций, `master.yaml`, `registry.yaml`,
    `model/releases/<версия>.json`, `_taken.yaml`;
  - `FileReleasedDescriptors` и `FileRegistryEntries` — чтение;
  - `ChangelogPaths` — общий компонент адресации для всех трёх (закрывает D03).

Порядок `ReleaseModel.execute` повторяет нынешний `_gen`:

1. собрать дескриптор;
2. решить по гейту;
3. при «выпускать нечего» вернуть исход без записи;
4. построить шаги и миграции;
5. пополнить занятые номера и пересобрать дескриптор в домене — повторно читать файлы
   не нужно;
6. собрать агрегат и передать его в `add`.

Текст миграций входит в агрегат, поэтому контракт записи принимает его целиком (закрывает D04).

Контрольные суммы реестра считаются в домене по тексту миграции, а не по файлу на диске. Это
то же значение `sha256`, что сейчас считает `registry.checksum`. Сверку неизменяемости
выпущенных файлов (`MDL-036`) выполняет `VerifyStore` через `RegistryEntries`: адаптер
пересчитывает сумму файла, а сравнивает домен.

**Альтернатива — текст миграции как готовое значение по CLAR-014 вне агрегата.** Отклонена:
текст выводится из модели и дельты правилами домена, это содержимое выпуска, а не внешнее
значение вроде идентификатора из другой системы.

### D7. Хранилище

Слои модуля `store`:

- **Домен** — правила целостности `IntegrityRule` по `MDL-015`: какие связи требуют проверки
  кардинальности и ацикличности, какие колонки ожидаются у таблицы ревизий. Сюда же переходит
  `SERVICE_COLUMNS` из `verify.py`. Ещё здесь сверка ожидаемого с фактом:
  `schema_drifts(expected, actual) -> tuple[SchemaDrift, ...]`.
- **Слой приложения** — контракты:
  - `SchemaInspector` — колонки и отпечаток версии;
  - `IntegrityQueries` — текст SQL по правилу;
  - `IntegrityProbe` — выполнить запрос и вернуть нарушения.
- **Инфраструктура** — `PostgresSchemaInspector`, `PostgresIntegrityQueries`,
  `PostgresIntegrityProbe` с открытием соединения через `psycopg`. Недоступное хранилище даёт
  `EnvironmentFault`, как сейчас.

`ListChecks` печатает тот же текст, что и сейчас: имя, предмет, SQL.

### D8. Цикл намерения

Нынешний `intent/` уже внедряет шаги. Раскладка доводит его до формы:

- **домен:**
  - `Stage`;
  - `StageOutcome` — бывший `Outcome`;
  - `Verdict`;
  - `IntentState` — бывший `State`, с машиной переходов;
  - `IterationReport` — становится неизменяемым;
  - правило засчитывания итерации;
- **слой приложения:**
  - контракт шага `Step` и `StepResult`;
  - сценарий `RunIntent` — бывший `run_cycle`;
  - контракты `ScenarioSource`, `StepsFactory`, `RunHistory` (чтение номера следующей
    итерации), `RunReports` (запись отчёта);
- **инфраструктура:** `YamlScenarioSource`, подставные шаги по сценарию `ScenarioSteps`
  (бывший `mock.py`), `FileRunHistory` и `FileRunReports`.

Ошибка процесса цикла остаётся `EnvironmentFault` с кодом `2`. Незамкнутый цикл — исход
с кодом `1`. Таблица `intent-pipeline` не меняется.

### D9. Файлы поставки

`delivery/infrastructure.py` — `PackageDeliveryFiles`. Он читает правила, глоссарий и образец
от корня поставки и вырезает раздел правила по заголовку: это знание формата Markdown, поэтому
место ему в инфраструктуре.

Сценарии `ShowNorms` (все нормы или одно правило) и `ShowSample` тонкие. Неизвестный код
правила — ошибка вызова (`EnvironmentFault`, код `2`), как в спеке `plugin-entry`. Домена
у модуля нет: правил предмета в нём нет, и пустой `domain.py` не создаётся.

### D10. Имена по глоссарию

Переименования:

| Сейчас | После | Понятие глоссария |
|--------|-------|-------------------|
| `Change` (`diff.py`) | `Operation` | Классы операций / операция дельты |
| `Relation` | `RelationSignature` | Сигнатура связи |
| `EnumDef` | `Enum` (стандартный модуль импортируется как `import enum`) | Перечисление |
| `Taken` | `TakenNumbers` | Занятые номера |
| `Operation` (`gen/ops.py`) | `MigrationStep` | Шаг миграции — новое |
| `Violation` (`checks.py`) | `IntegrityViolation` | Нарушение целостности — новое |
| `Drift` (`verify.py`) | `SchemaDrift` | Расхождение схемы — новое |
| `Outcome` (`intent/step.py`) | `StageOutcome` | Исход стадии — новое |
| `State` (`intent/state.py`) | `IntentState` | Состояние намерения — новое |
| `Scenario` (`intent/scenario.py`) | `RunScenario` | Сценарий прогона — новое |

В `plugin/forge/share/docs/glossary.md` добавятся понятия:

- «Шаг миграции», «Нарушение (Finding)», «Место (Place)», «Значение перечисления (Enum Value)»,
  «Версия (Version)», «Агрегат выпуска (Release)»;
- «Нарушение целостности», «Расхождение схемы»;
- раздел «Цикл намерения»: «Стадия (Stage)», «Исход стадии», «Вердикт (Verdict)»,
  «Состояние намерения», «Отчёт итерации (Iteration Report)», «Сценарий прогона».

Для понятия «Выпуск (Release)», которое уже есть в глоссарии, уточняется определение:
выпуск — агрегат записанных файлов версии.

Тест имён перебирает неизменяемые классы всех `domain.py`. Английское имя понятия сравнивается
с именем класса без пробелов; для понятий во множественном числе допускается единственное
(`Integrity Checks` → `IntegrityCheck`).

### D11. Эталоны и тесты архитектуры

Первым шагом, до раскладки, фиксируется эталон `tests/golden/`. Он получается прогоном
нынешнего кода с фиксированными часами на фикстурах `forge.reqs.v1` и `trade.v1`:

- дескриптор;
- миграции выпуска двух версий и свёртки;
- `master.yaml` и `registry.yaml`;
- вывод `build`, `diff`, `checks`.

Тест эталона сравнивает побайтно и остаётся после change регрессионным: выпущенные файлы
живут у потребителей, и любое будущее изменение их байтов должно быть заметно.

Тесты архитектуры — `tests/test_architecture.py` на `ast`, без новых зависимостей:

- направление импортов по слоям и модулям; `yaml` и `psycopg` — только инфраструктура;
- у каждого сценария одна публичная операция `execute`, а `Input` и `Output` — `frozen`
  без методов;
- классы `domain.py` с `@dataclass` — `frozen`;
- конструкторы сценариев-запросов не принимают контракт записи;
- имена по глоссарию (D10).

Пока раскладка не закончена, тест архитектуры проверяет только переложенные модули. Перечень
переложенных модулей лежит в самом тесте и растёт с каждой группой задач. В последней группе
он заменяется обходом всего пакета.

### D12. Порядок раскладки

Модули перекладываются по одному, от листьев к корню зависимостей:

1. `delivery`;
2. `contract` — модель, правило, дескриптор, дельта, гейт;
3. `release`;
4. `store`;
5. `intent`;
6. вход и сборка.

После каждого шага весь набор зелёный: старые плоские модули удаляются в том же шаге,
что и их перенос, а модульные тесты переводятся на новые пути там же. Переходных реэкспортов
нет — внутренних потребителей, кроме тестов и `cli.py`, у модулей нет.

## Risks / Trade-offs

- [Изменится хеш или байты дескриптора] → эталон D11 фиксируется до первой правки и сравнивается
  побайтно на каждом шаге.
- [Метки строк `yaml.compose` для однострочных отображений `{ id: 1, … }` указывают на начало
  отображения, а не на ключ] → место нарушения поля — строка записи поля; этого достаточно для
  `MDL`-файлов, где одно поле — одна строка; тест модели с двумя дефектами проверяет обе строки.
- [Объём: перекладывается весь пакет] → группы задач по модулю, каждая завершается зелёным
  набором и проходит независимую проверку; тест архитектуры растёт вместе с раскладкой.
- [Разовые классы расхождения в каждом модуле дублируют форму] → форма из двух полей, и тест
  архитектуры сверяет её единообразие; общий модуль нарушил бы CLAR-023.
- [Протоколы без наследования скрывают, кто что реализует] → фабрика сборки аннотирована
  контрактом, mypy проверяет совместимость при каждой сборке.
- [Перечень всех нарушений меняет вывод отказа] → изменение заявлено в дельте `model-contract`;
  код возврата прежний; навык `forge:model-change` читает вывод как текст и не зависит от числа
  строк.

## Migration Plan

Миграции данных нет. Потребитель получает новое ядро обновлением плагина. Выпущенные файлы
не меняются: это гарантирует эталон D11. Откат — возврат версии плагина. Версия плагина
в `plugin.json` и `pyproject.toml` поднимается до `0.2.0`: изменился вывод отказа модели.
